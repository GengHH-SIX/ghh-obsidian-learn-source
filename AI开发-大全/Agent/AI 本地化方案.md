结合市面上的主流实践，我把开发「本地可执行命令的 AI Agent」的常用方法按技术路线和开发门槛分成四大类，每类只讲方法逻辑、适用场景和代表方向，不展开具体工具的开发步骤：


---

## 🔗落地方案
### 一、基于成熟 Agent 框架二次开发（最主流）

这是目前绝大多数开发者的首选，核心是用现成的开源 Agent 框架当底座，你只需要定义工具、提示词和业务逻辑，框架帮你搞定「模型调用 → 规划推理 → 工具选择 → 命令执行 → 结果反馈」的完整闭环。

  

- 核心原理：框架已经封装好了 ReAct（推理-行动-观察）循环、工具注册机制、记忆管理、错误重试等通用能力，你把本地命令行能力作为一个「工具」注册进去，模型就能自主决定何时调用终端执行命令。

- 典型路线：

  1. 通用编排框架路线：用 LangGraph、CrewAI、AutoGen 这类通用 Agent 框架，自己封装一个 shell 执行工具函数，注册后 Agent 就能按需调用本地命令。

  2. 低代码可视化路线：用 Dify、n8n 这类带界面的平台，通过节点拖拽编排流程，把「本地命令执行」作为一个自定义节点接入，适合不想写太多代码的场景。

  3. 专用终端 Agent 框架路线：基于 Open Interpreter、AutoGPT 这类天生就带终端执行能力的开源项目做二次开发，省去自己封装 shell 工具的步骤。

- 适用场景：想快速做出可用产品、不想从零造轮子、需要后续持续扩展更多工具（联网、文件操作、API调用等）的项目。

  

---

  

### 二、直接用大模型 SDK 从零手写（最灵活）

完全不依赖 Agent 框架，只用大模型官方 SDK + 自己写的命令执行函数，手动实现「思考-执行-反馈」循环。

  

- 核心原理：你自己写一个 while 循环，每一轮把用户目标 + 历史执行结果喂给大模型，让模型输出「要执行什么命令」，你在本地安全执行后把 stdout/stderr 回传给模型，模型再根据输出决定下一步，直到任务完成。

- 典型路线：

  1. 纯函数调用模式：利用大模型的 Function Calling / Tool Calling 能力，把「执行 shell 命令」定义成一个函数，模型自动触发调用，你负责执行并返回结果。

  2. 纯提示词驱动模式：不靠函数调用接口，完全通过提示词约束模型输出格式（比如用 `` 标签包裹命令），你解析输出后执行再回传，兼容任何大模型。

- 适用场景：需要完全掌控执行逻辑、对安全性要求极高（想做精细的命令白名单/黑名单、沙箱隔离）、或者项目极简单不想引入重型框架的场景。

  

---

  

### 三、基于 MCP（模型上下文协议）的工具接入模式（新标准）

这是 2025 年以来快速普及的新路线，核心是把本地命令执行能力封装成 MCP Server，任何兼容 MCP 协议的 AI 客户端都能直接调用。

  

- 核心原理：MCP 是一套标准化的工具连接协议，你不用关心上层 Agent 用什么框架写，只要把本地终端能力打包成一个 MCP 服务，所有支持 MCP 的 AI 工具（比如 Claude Desktop、各类 AI IDE、Agent 框架）都能直接「发现」并调用这个能力，实现一次封装、到处可用。

- 典型路线：

  1. 封装本地终端 MCP Server：把 shell 命令执行、文件系统操作封装成标准 MCP 工具，接入到你自己的 Agent 或第三方 AI 客户端里。

  2. CLI-Anything 路线：把各类专业软件（设计工具、3D建模、多媒体编辑等）重新包装成命令行接口，再通过 MCP 暴露给 Agent，让 Agent 能直接驱动原本需要人工操作的复杂软件。

- 适用场景：想让 Agent 能力复用在多个 AI 客户端上、追求标准化对接、或者需要接入大量异构工具的项目。

  

---

  

### 四、基于现成 AI 编程/终端 Agent 产品扩展（最低成本）

不自己从零开发 Agent 内核，直接用已经自带终端执行能力的产品级 Agent，在它之上做自定义扩展。

  

- 核心原理：这类产品本身就已经实现了「本地命令执行 + 文件读写 + 代码运行」的完整能力，你只需要通过它的插件/扩展机制，加上你自己的业务逻辑、定制工具或专属工作流，就能得到符合自己需求的本地 Agent。

- 典型路线：

  1. AI 编程工具扩展：在 Cursor、Claude Code、Kimi Code 这类天生带终端操作能力的 AI IDE/CLI 工具基础上，通过自定义指令、Skills、插件体系扩展专属能力。

  2. 桌面 AI 助手扩展：在支持本地工具调用的桌面 AI 客户端里，通过 MCP 或插件机制接入自定义的命令执行能力，变成你专属的本地执行 Agent。

- 适用场景：主要用于个人效率提升、开发辅助，不想花时间做底层工程，只想快速用上「能帮我跑命令的 AI」。

  

---

  

### 一句话选型建议

- 想快速做产品 → 选第一类，用成熟 Agent 框架二次开发

- 要完全可控、高度定制 → 选第二类，自己从零手写

- 想一次开发、多端复用 → 选第三类，走 MCP 标准协议

- 只是个人用、提升效率 → 选第四类，直接在现成产品上扩展

## 👶Vibe Coding 环境搭建

### 一、安装 CC Switch

- 简介
 CC Switch 可以帮你在 Claude Code / Codex / Gemini CLI 的多个供应商之间一键切换。如果你之前已经配置过这些工具，CC Switch 会自动把现有设置保存为名为 “default” 的供应商，保证你的配置不会丢失。

列表里还预置了 “官方（Official）” 供应商，随时点一下即可切回官方默认配置。切换前 CC Switch 会自动把当前配置备份回 default，可以放心来回切。CC Switch 就是这样工作的 😊

- 安装
```bash
brew install --cask cc-switch
```
 
 - 用途
切换不同的大模型源，方便在使用codeing 工具（比如：claude）时能方便的切换想要使用的大模型；同时也避免了在使用`claude`的时候能使用国内的大模型；而不是只能在它官网上充值，且只能使用它内置的几个大模型！

### 二、安装 warp 终端工具

- 安装
```bash
brew install --cask warp
```

- 用途
界面更加友好，支持分屏操作，能在同一项目的目录下，分别执行不同的操作等等！
