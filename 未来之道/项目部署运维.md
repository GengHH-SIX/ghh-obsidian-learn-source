# docker & k8s集群

是的，只要在生产环境使用了 Kubernetes (K8s) 集群部署，就不再需要 Docker Compose 了。

在软件开发和运维的生命周期中，Docker Compose 和 Kubernetes 属于同一个生态，但它们各司其职，处于不同的阶段：

- Docker Compose 的定位是本地开发与测试的利器。它极其轻量，能让你在单机（比如你的 Mac 电脑）上用一个 YAML 文件快速把一整套多容器应用跑起来。
- Kubernetes 的定位是生产级别的集群操作系统。它专门为了在多台服务器（集群）上实现高可用、全自动扩容、自我修复、滚动更新和复杂的网络路由而设计。

当你的应用走向生产环境并部署到 K8s 集群中时，K8s 的资源对象（Deployment、Service、Ingress 等）会完全接管并替代 Compose 的所有功能。

---

## 🔄 它们在功能上的“完全替代”关系

在 K8s 中，你再也不需要编写 `docker-compose.yml`，因为 K8s 的 YAML 规范提供了更强大、更大规模的替代方案：

|你的需求|在 Docker Compose 中（单机）|在 Kubernetes 中（生产集群）|
|---|---|---|
|定义容器如何运行|使用 `services.image`|使用 Deployment (定义 Pod 副本、镜像、资源限制) [1]|
|容器之间相互访问 / 负载均衡|使用 `links` 或自定义 `networks`|使用 Service (通过 ClusterIP 自动做服务发现和内部负载均衡) [1]|
|把网站通过域名发布给外网|使用 `ports: - "80:80"` (直接占满宿主机端口)|使用 Ingress + Ingress Controller (单 IP、多域名智能分流)|
|数据持久化|使用 `volumes` 挂载本地目录|使用 PersistentVolume (PV) 和 PVC (支持对接云盘、分布式存储)|
|配置和密钥管理|使用 `environment` 或 `.env` 文件|使用 ConfigMap 和 Secret (加密存储，动态更新不重启容器)|

## 🏗️ 为什么生产环境必须要“丢弃” Compose 拥抱 K8s？

如果强行在生产环境使用 Docker Compose，会遇到很多致命的瓶颈，而这些正是 K8s 的核心优势：

1. 单机 vs 多机（高可用）
    
    - Compose：只能在一台服务器上跑。如果这台服务器硬件坏了、断网了，你的网站就彻底瘫痪了。
    - K8s：管理成百上千台服务器。如果节点 A 意外宕机，K8s 会秒级发现，并自动把节点 A 上的容器在节点 B、C 上重新拉起来（自我修复 / Self-healing），用户完全无感知。
    
2. 弹性伸缩（Scaling）
    
    - Compose：如果遇到突发大流量（比如双十一、搞活动），你必须手动登录服务器去敲命令加实例，而且单台机器的 CPU/内存是有上限的。
    - K8s：支持 HPA (水平 Pod 自动扩容)。当监测到 CPU 压力超过 80% 时，K8s 会自动在整个集群里把投票容器从 1 个克隆到 10 个甚至 100 个，流量下降后又自动缩容，全自动省心省钱。
    
3. 零停机更新（Rolling Update）
    
    - Compose：更新版本时，通常需要重启容器，这会导致网站出现短暂的断连或报错（502）。
    - K8s：采用滚动更新。它会先启动一个新版 V2 容器，等新容器完全健康后，再把老版 V1 容器流量切过来并销毁老容器，整个升级过程用户正在点击网页却完全不受影响。

## 💡 现在的标准企业流水线（Workflow）是怎样的？

虽然生产环境不要 Compose，但并不意味着你要把它删掉。绝大多数科技公司目前采用的黄金组合是：

- 开发阶段（你的 Mac 电脑上）：使用 Docker Compose（或者像你现在这样用 OrbStack 跑一个微型 K8s）。因为 Compose 启动极其快速，改了代码能立刻看到效果，资源占用极小。
- 测试/生产阶段（云服务器集群）：代码通过 Git 提交后，触发 CI/CD 自动化流水线（如 GitHub Actions、Jenkins），直接将编写好的 K8s YAML 规格说明书 部署到 Kubernetes 集群中。

# DNS域名配置（单IP多域名）

==不能，`192.168.194.20` 绝对不能用来作为生产环境部署域名。== [1]

这个 IP 是 OrbStack 在你的 Mac 电脑内部虚拟出来的一个局域网私有 IP（属于 RFC 1918 规定的私有地址段） [1]。除了你自己的这台 Mac 电脑，外界的任何用户、甚至和你同一路由器下的同事，都无法通过这个 IP 访问到你的网站。

在真实的生产环境中，要让全世界的用户通过域名访问你部署在 Kubernetes（K8s）集群里的网站，标准且主流的做法是使用 Ingress Controller（入口控制器）。

## 🌐 生产环境通过域名发布网站的 4 个标准步骤

## 第一步：准备好云厂商的负载均衡器 (LoadBalancer)

在阿里云、腾讯云、AWS 或 GCP 等云厂商购买 K8s 集群（如 ACK、EKS）时，Kubernetes 可以直接与云厂商的底层网络联动。

## 第二步：部署 Ingress Controller

生产环境一般不直接用 `NodePort`（因为带端口很难看），也不用 OrbStack 这种本地特有的 IP [1]。我们在集群里部署一个网关，最常用的是 Nginx Ingress Controller。

1. 当你部署了 Ingress Controller 后，云厂商会自动为你分配一个公网 IP（例如 `47.100.x.x`）。
2. 这个公网 IP 会作为你整个集群的唯一流量入口。

## 第三步：配置域名解析 (DNS)

前往你的域名服务商（如阿里云解析、GoDaddy），添加一条 A 记录，将你的生产域名指向刚刚获取的公网 IP：

- 主机记录：`vote` 或 `www`
- 记录类型：`A`
- 记录值：`47.100.x.x`（云厂商给的公网 IP）

## 第四步：在 K8s 中编写 Ingress 转发规则 (YAML)

最后，你在 K8s 里提交一个 `Ingress` 资源文件。它的作用是告诉网关：当有访问 `://yourdomain.com` 的流量进来时，请把它转发给 `vote` 这个 Service。

高级的生产环境配置示例（YAML）：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: voting-app-ingress
  annotations:
    kubernetes.io/ingress.class: "nginx"
    nginx.ingress.kubernetes.io/ssl-redirect: "true" # 生产环境通常强制跳转 HTTPS
spec:
  tls:
  - hosts:
    - ://yourdomain.com
    secretName: yourdomain-tls-cert # 配置你的 SSL 证书
  rules:
  - host: ://yourdomain.com  # 你的生产域名
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: vote-service # 转发给你的投票服务
            port:
              number: 80       # 服务的端口
```

---

## 🎯 为什么生产环境要这么做？

1. 统一入口，节约成本：你只需要绑定一个公网 IP 并在云厂商处付一个 IP 的钱。后续无论你的集群里增加几百个网站（如 `://yourdomain.com`、`://yourdomain.com`），都只需要在 Ingress 里加几行配置，用同一个公网 IP 就能通过不同的域名路由到不同的容器。
2. 安全与证书管理：你的 SSL/TLS 证书（HTTPS 加密）可以直接配置在 Ingress 这一层。容器内部不需要理会证书，网关会自动帮你把 HTTPS 解密成 HTTP 再传给容器。
3. 动态扩容无感知：无论底下的容器（Pod）怎么死掉、重建、IP 怎么变，外面的域名和 Ingress 都不需要做任何修改，K8s 内部会自动做好平滑对接。
